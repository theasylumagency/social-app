# T10/T11 — შენიშვნების აღდგენადი დამუშავება და პოსტის ცალკე ვერსია

შენიშვნის გაგზავნა ახლა სწრაფად ინახავს მიღებულ ტექსტს და აბრუნებს პასუხს. მოდელის მუშაობა და ცვლილების შესრულება ფონურად გრძელდება. დამტკიცებული პოსტის ერთი არხის შესწორება ქმნის დამოუკიდებელ ვერსიას; კვირის გეგმა, სხვა ტექსტები და განრიგები ავტომატურად არ იცვლება.

## მომხმარებლის გზა

1. დაწერეთ ან ხმით დაამატეთ შენიშვნა. ტექსტი, არჩეული ობიექტი და მოთხოვნის იდენტიფიკატორი მონახაზში ინახება მომხმარებლის, ბრენდის, გვერდისა და კვირის მიხედვით.
2. გაგზავნის შემდეგ ჩანს, რომ შენიშვნა მიღებულია. გვერდის განახლება, დაკარგული პასუხი და პროცესის შეწყვეტა ჩანაწერს არ კარგავს. უკვე შესრულებული მოთხოვნა ხელახლა არ სრულდება.
3. ფართო ცვლილებისას არსებული დადასტურება/უარყოფა/დაბრუნება შენარჩუნებულია. დასრულებულ, ჯერ დაუმტკიცებელ პოსტზე შესწორება კვლავ მოქმედ ტექსტს აახლებს და ახალ შეფასებას ითხოვს.
4. დამტკიცებულ პოსტზე მხოლოდ არჩეული არხის ახალი ტექსტი ცალკე ინახება. ჩანს ძველი/ახალი ტექსტი, შეფასების მდგომარეობა და კონკრეტულ პოსტებზე გავლენა.
5. ახალ ტექსტს საკუთარი ფაქტობრივი და სარედაქციო შემოწმება და თქვენი ახალი დამტკიცება სჭირდება. შემოწმება კვირის ტექსტებსაც ადარებს გამეორებისა და კონფლიქტების დასადგენად; სხვა პოსტებს არ წერს.
6. დამტკიცების შემდეგ განრიგში მიმდინარე ვერსია გამოჩნდება. ძველი განრიგის ჩანაცვლება კვლავ ცალკე გადასამოწმებელი მოქმედებაა და მხოლოდ შესაბამის პოსტსა და არხს ეხება.
7. გაგზავნის ნებისმიერი დაწყებული მცდელობა ჩანაცვლებას ბლოკავს, მათ შორის უცნობი შედეგი. ისტორიული ტექსტი, დამტკიცება და შედეგი შენარჩუნებულია. გამოქვეყნებული პოსტის პროვაიდერთან რედაქტირება ამ ფუნქციის ნაწილი არ არის.

## შესრულება და აღდგენა

`contextual_notes` არის მიღებული მოთხოვნის მუდმივი ჩანაწერი. `job_kind` გამოყოფს გაგების ეტაპს ცვლილების შესრულებისაგან. გაგების შედეგი ჯერ ინახება; ავტომატური მოქმედება შემდეგ ცალკე claim-ით სრულდება, ამიტომ ამ ორ ეტაპს შორის შეწყვეტა გაგების მოდელს ხელახლა არ იძახებს.

მუშაობას lease/token და heartbeat იცავს. ვადაგასულ სამუშაოს ახალი პროცესი იღებს, ხოლო ძველი token ვეღარ წერს შედეგს ან ასრულებს ცვლილებას. ცვლილება და შენიშვნის დასრულების ჩანაწერი ერთ ტრანზაქციაში ინახება. ავტომატური აღდგენა შეზღუდულია სამი ცდით; ხელით ხელახლა ცდა იმავე ID-ს იყენებს და საათში სამი ცდით არის შეზღუდული. ყველა claim გადამოწმებულ მომხმარებელს, მოქმედ გამოწერასა და ბრენდის მფლობელს ამოწმებს.

აპლიკაციის ფენა ფლობს გაგების კონტრაქტს, გადაწყვეტილებას, შესრულების ავტორიზაციასა და შესწორების ზუსტ არეს. PostgreSQL ადაპტერი ფლობს შენახვას, claim-ს, lock-სა და ატომურ ჩანაწერს. გაგების ცალკე პორტი იღებს სრულ თავდაპირველ ტექსტს და კონტექსტს; ალტერნატიულმა ინტერპრეტატორმაც საერთო schema, ზუსტი ციტატები და კვირის პირობების კონტრაქტი უნდა გაიაროს. მოქმედი ინტერპრეტატორი იგივე რჩება. Jev არ ჩართულა.

ოპერატორს ორი დამოუკიდებელი რიგი დაემატა: `notes` და `post-revisions`. სხვა ოთხი AI რიგისა და delivery/maintenance პროცესების გამოყოფა შენარჩუნებულია. ახალი რიგებიც `OPERATOR_QUEUE_CONCURRENCY`-ით იზღუდება. ფონური შესწორება იყენებს გაგების ერთ ნაბიჯს, არჩეული ტექსტის ერთ writer-ს და პარალელურ ფაქტობრივ/სარედაქციო reviewers-ს; სხვა პოსტების writer-ებს და კვირის დაგეგმვას არ იწყებს. რეალური დროისა და ხარისხის ცვლილება T12-ში გასაზომია — mock ტესტები ხარისხის ბენჩმარკი არ არის.

## ვერსია, დამტკიცება და განრიგი

`post_revisions` ინახავს საწყის და ახალ payload-ს, გაყინულ გეგმის კონტექსტს, წინა ვერსიის ID-ს, საწყისი კვირის დამტკიცებას და ტექსტის digest-ს. ერთი ლოგიკური პოსტის ID შესწორებებში აშკარად მემკვიდრეობით გადადის; არხს თავისი ვერსიის ნომერი აქვს. ახალი, თავიდან გენერირებული კვირის გეგმის პოსტები სათაურის ან პოზიციის მსგავსების გამო ძველ პოსტებად არ ითვლება.

მოდელს არჩეული ტექსტის გარდა სხვა არხის, პოსტის ან outline-ის შეცვლა არ შეუძლია. ახალი დამტკიცება გადაიმოწმებს საწყის გეგმას, ბრენდის საფუძველს, სტრატეგიას, ფაქტების ნებართვებს, წესებს და წინა დამტკიცებულ ვერსიას. პარალელურ შესწორებებს საერთო გაყინული კვირის კონტექსტი აქვთ; უკვე დამტკიცებული სხვა შესწორების შემდეგ მოძველებული proposal ახალი შენიშვნით უნდა მომზადდეს.

ახალი ტექსტი გამოქვეყნების **V4** პაკეტში ინახება: მას აქვს საკუთარი approval, review, პოსტის მუდმივი ID, არხი, ვერსია და საწყისი ტექსტის კავშირი. V1/V2/V3 readers და ძველი პაკეტების ფორმები მხარდაჭერილია. ძველი კვირის approval ახალ V4 ტექსტს ვერ ამტკიცებს; V4-ის მტკიცებულების მოცილებით V3-ად scheduling-იც არ დაიშვება.

განრიგის შენახვა კვლავ ერთ ტრანზაქციაში სრულდება. ახალ ჩანაწერს თავისი input/draft/schedule აქვს. მოსალოდნელი წინა input ID-ები ზუსტად უნდა ემთხვეოდეს მიმდინარე მდგომარეობას; შეცდომა მთელ ჯგუფს აბრუნებს. საწყისი კვირის ჩანაწერი და სხვა პოსტებისა თუ არხების განრიგები უცვლელი რჩება. ძველი რიგიდან წინასწარ წაკითხული ჩანაწერი ჩანაცვლების შემდეგ გაგზავნის უფლებას კარგავს.

მოკლე ჩამონათვალი აბრუნებს ბოლო 20 ვერსიას, თითოეული არხის მიმდინარე დამტკიცებულ ვერსიას და ბოლო ღია ვერსიას (მაქსიმუმ 60 ჩანაწერი). ამიტომ ახალი წარუმატებელი ვერსიები მიმდინარე დამტკიცებულ ტექსტს არ მალავს. სრული გეგმის payload და მოდელის traces ბრაუზერს არ ეგზავნება.

## შემოწმება და ჩართვა

შემოწმების ზუსტი შედეგები და ფაილების SHA-256 ცალკე verification ჩანაწერშია. ტესტები რეალურ ლოკალურ PostgreSQL-ზე მხოლოდ შემთხვევითი სახელის იზოლირებულ სქემებს იყენებს. ბრაუზერში ნამდვილი კომპონენტები სატესტო პასუხებით შემოწმდა: 390px ეკრანი, ძველი/ახალი ტექსტი, ცალკე დამტკიცება, მონახაზის აღდგენა და კლავიატურით გაგზავნა. პროვაიდერთან რეალური გამოქვეყნება და ფასიანი მოდელების ბენჩმარკი არ შესრულებულა. ხმის სამწამიანი სიჩუმის წესი უცვლელია.

სამუშაო ბაზაზე მიგრაციები ამ ეტაპზე **არ გაშვებულა**. საჭიროა არსებული 0020–0023 და ახალი 0024–0025. ჩართვის რიგი:

1. დაასრულეთ ან შეწყვიტეთ ძველი API-ის ხანგრძლივი notes მოთხოვნები; გააჩერეთ AI worker და ახალი scheduling/delivery სამუშაოების მიღება.
2. არსებულ migration პროცესში გაუშვით 0020–0025 და გადაამოწმეთ schema. უკვე შენახული `processing` notes ახალ რიგში გადავა; ძველი inline პროცესები ამ დროს აღარ უნდა მუშაობდეს.
3. API და ყველა worker იმავე გამოშვებაზე განაახლეთ. V4 მონაცემის შექმნამდე delivery worker-ის V4 reader უნდა იყოს მზად.
4. სატესტო ბრენდზე გადაამოწმეთ მიღება, პროცესის აღდგენა, შეფასება, ახალი დამტკიცება და ჯერ გაუგზავნელი განრიგის ჩანაცვლება; შემდეგ განაახლეთ რიგების ჩვეულებრივი მუშაობა.
5. უკანდახევისას შეაჩერეთ ახალი სამუშაო და შეინარჩუნეთ V4-ის კითხვა. V4-ის შექმნის შემდეგ ძველ, მხოლოდ V1–V3 binary-ზე პირდაპირ დაბრუნება თავსებადი აღარ არის. გამოქვეყნებული ან უცნობი შედეგის ჩანაწერი ხელახლა არ იგზავნება.

შემდეგი სამუშაოა **T12**: ხარისხის რეალური შეფასების ნაკრები, დროის/ტოკენების/შესწორებების გაზომვა და Jev-ის ვიწრო ინტერპრეტაციის კანდიდატის შედარება იმავე პირობებზე. ამ მონაცემების შემდეგ გადაწყდება, ღირს თუ არა მოდელის შეცვლა რომელიმე კონკრეტულ გზაზე.
