# პოსტების შეწყვეტის დიაგნოსტიკა და worker-ის დაცვა

მომხმარებლის მოწოდებული გეგმა არის სკაპის 2026-10-05 კვირის პირველი ვერსია. მოწოდებულ ლოგში სამუშაოს იდენტიფიკატორია `c7979442-689f-46ac-aee8-9794dd03aa53`.

## რა დადასტურდა

- კვირის სტრატეგიული გეგმის დავალება დასრულდა დაახლოებით 29.8 წამში. პოსტების პროცესის ორი მცდელობა შეწყდა `outline` ეტაპზე, შესაბამისად დაახლოებით 78.3 და 99.3 წამში. ორივე ჩანაწერში მიზეზია `contract`: მოდელის პასუხმა აპლიკაციის მოთხოვნები ვერ დააკმაყოფილა. ლოგი არ აჩვენებს, რომელი კონკრეტული მოთხოვნა დაირღვა.
- ამ ორ წარუმატებელ მცდელობაში არჩეული მოდელია `gpt-5.6-terra`. აქედან ჯერ ვერ დგინდება, ახლანდელი worker ისევ ძველ პარამეტრებს იყენებს თუ ჩანაწერი განახლებამდე შეიქმნა: მიწოდებულ ლოგს დროის ნიშნები არ ახლავს.
- PostgreSQL-მა ერთ შემთხვევაში კავშირი შეწყვიტა კოდით `57P01`, რის შემდეგაც დაუმუშავებელი pool-ის `error` მოვლენა Node-ის პროცესს აჩერებდა. ეს დამოუკიდებელი ოპერაციული ხარვეზია; იგი არ ადასტურებს ბოლო `contract` შეცდომის მიზეზს.
- გაშვების ბრძანება კითხულობს `.env.local`-ს. მომხმარებელმა დაადასტურა, რომ ახალი პარამეტრები სწორედ ამ ფაილში ჩაწერა.

`OPENAI_POST_PLANNER_MODEL` პრიორიტეტულია `OPENAI_PLANNING_MODEL`-თან შედარებით. ამიტომ ცალკე ძველი planner მნიშვნელობა შეიძლება დარჩეს მოქმედი, მაშინაც კი, როცა საერთო planning მოდელი განახლებულია. დამატებით, პროცესის გარემოში უკვე არსებული მნიშვნელობა Node-ის `--env-file`-დან მიღებულ იმავე ცვლადს სჯობს. PM2-ის გარემოს განახლებისთვის გამოიყენება `--update-env`; თუ ecosystem ფაილი ან გაშვების გარემო ძველ მნიშვნელობას აწვდის, ისიც უნდა გასწორდეს. ეს ამ შემთხვევის შესაძლო მიზეზებია და არა უკვე დადასტურებული დიაგნოზი. [Node-ის გარემოს ჩატვირთვა](https://nodejs.org/api/cli.html#--env-filefile), [PM2-ის გარემოს განახლება](https://pm2.keymetrics.io/docs/usage/process-management/#updating-environment-variables-and-options).

## განხორციელებული შესწორება

worker-ის AI, გამოქვეყნების და ანალიტიკის კავშირები ახლა საერთო დაცულ pool-ს იყენებს. უმოქმედო კავშირის შეცდომა აღირიცხება მოკლე კოდით; კავშირის ობიექტი და მისი შიგთავსი ჟურნალში არ იბეჭდება. pg წყვეტილ კავშირს თვითონ აშორებს pool-ს; შემდეგ მოთხოვნას შეუძლია ახალი კავშირი გახსნას. აქტიური მოთხოვნების შეცდომები კვლავ დამძახებელთან ბრუნდება და შესრულების არსებული წესები არ იცვლება. [pg-ის ოფიციალური აღწერა](https://node-postgres.com/apis/pool#events).

worker-ის არსებული მაქსიმალური კავშირების რაოდენობები და მათი გაყოფა შენარჩუნებულია. ახალი კავშირის ლოდინის ზღვარია ხუთი წამი, რის შემდეგაც არსებული ციკლი შეცდომას აღრიცხავს და შემდგომ ცდაზე აგრძელებს მუშაობას. ვებაპლიკაციის საერთო pool-საც იგივე უმოქმედო კავშირის დაცვა აქვს.

AI worker გაშვებისას წერს `Operator AI configuration` ჩანაწერს დროით, პროცესის ნომრით და პოსტების სამ ეტაპზე რეალურად არჩეული მოდელით/მსჯელობის დონით. ამ ჩანაწერში გასაღები, ბაზის მისამართი და ბრენდის მასალა არ შედის.

დაემატა `scripts/weekly-posts-diagnostics.mts`: ის კითხულობს მხოლოდ მითითებულ გეგმას, პოსტების პროცესის მდგომარეობას და ბოლო მაქსიმუმ 20 მოდელურ მცდელობას. თითო მცდელობიდან მაქსიმუმ 12 ვალიდაციის შეტყობინება გამოაქვს, თითოეული 600 სიმბოლომდე. ინახავს დროს, მოდელს, დონეს, ტოკენების რაოდენობას და შედეგს. მოთხოვნები ტარდება ერთი `READ ONLY` ტრანზაქციით და 10-წამიანი SQL ზღვარით; ბოლოს ტრანზაქცია იხურება. იგი არ იძახებს AI-ს და მონაცემებს არ ცვლის.

დიაგნოსტიკაში მოცემული `cliPostConfiguration` ამ ცალკე ბრძანების გარემოს აჩვენებს. უკვე გაშვებული PM2 პროცესის პარამეტრების მტკიცებულება მისი ახალი startup ჩანაწერი ან მიმდინარე მოდელური მცდელობის `reasoning_effort`/`model` მონაცემებია.

## სერვერზე შემდეგი ნაბიჯი

1. ატვირთეთ ეს ცვლილებები ჩვეულებრივი განახლების წესით. ბაზის ახალი მიგრაცია არ არის საჭირო. ვებაპლიკაციის საერთო pool-ის ცვლილებისთვის საჭიროა ახალი build; worker-ისთვის — განახლებული კოდით ხელახლა გაშვება.
2. სერვერზე შეამოწმეთ მოდელის ცალკე სამი პარამეტრიც: `OPENAI_POST_PLANNER_MODEL`, `OPENAI_POST_WRITER_MODEL`, `OPENAI_POST_REVIEW_MODEL`. შეთანხმებული საცდელი მოდელი სამივეზე არის `gpt-6.1-sol`; დაგეგმვისა და წერის დონე — `medium`, შემოწმების — `low`. შეამოწმეთ იგივე ცვლადები PM2-ის ecosystem კონფიგურაციაშიც, თუ ის გამოიყენება.
3. შესაბამისი PM2 პროცესის განახლებისას გამოიყენეთ `--update-env`. ლოგის სახელიდან ნავარაუდევი worker-ის სახელი არის `unda-worker`; გადაამოწმეთ `pm2 list`-ში, შემდეგ:

```bash
pm2 restart unda-worker --update-env
```

4. რეალური პარამეტრები ნახეთ ახალ `Operator AI configuration` ჩანაწერში. შემდეგ კონკრეტული შეწყვეტილი გეგმის დიაგნოსტიკა გამოიტანეთ:

```bash
cd /var/www/unda-app
node --env-file=.env.local --import tsx scripts/weekly-posts-diagnostics.mts c7979442-689f-46ac-aee8-9794dd03aa53
```

5. `validation_errors` და მოდელის მონაცემებით განისაზღვრება პოსტების გეგმის ზუსტი შესწორება. ეს მიზეზი არსებული მასალით ჯერ დაუდგენელია; ფაქტების, არხების, რაოდენობის და ფორმატების შემოწმება არ შესუსტებულა. შემდგომი ცდა შეიძლება არსებული გეგმიდან გაკეთდეს — ხელახლა ბრენდის გაცნობა საჭირო არ არის.

## შემოწმება

დაცვა გადამოწმდა რეალურ ადგილობრივ PostgreSQL-ზე: შეწყდა მხოლოდ ტესტის მიერ შექმნილი უმოქმედო კავშირი და შემდეგი მოთხოვნა ახალი კავშირით წარმატებით შესრულდა. დიაგნოსტიკის SQL ცალკე დროებით სქემაში შემოწმდა: ერთი გეგმის მონაცემები შეირჩა, სხვა გეგმა და ტექსტები ანგარიშში არ მოხვდა, `ROLLBACK` დასრულდა. ორივე ინტეგრაციის ტესტი წარმატებულია, გამოტოვებული ტესტების გარეშე.

ტიპებისა და მიზნობრივი ოფლაინ ტესტების შემოწმებაც დასრულებულია. `npm run verify` წარმატებულია: 311 domain და 229 application ტესტი — ჯამში 540 ტესტი, ნული ჩავარდნა და ნული გამოტოვება. კოდის სტილის შემოწმებას აქვს ექვსი არსებული გაფრთხილება და ნული შეცდომა. Production build დასრულდა წარმატებით. ორი მიზნობრივი PostgreSQL ინტეგრაციის ტესტი ცალკე შესრულდა; სრული ინტეგრაციის ნაკრები ამ ცვლილებისთვის არ გამეორებულა. სერვერზე შესწორების გავრცელება და ამ გეგმის საბოლოო წარმატებული გენერაცია ჯერ გადასამოწმებელია.
