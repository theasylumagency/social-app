# პოსტების არხების შეცდომის გამოსწორება

ეს ჩანაწერი აგრძელებს [worker-ის დაცვისა და დიაგნოსტიკის ანგარიშს](2026-10-11-worker-recovery-and-posts-diagnostics.md). თავდაპირველი ანგარიშის დასკვნები აღწერს იმ დროს ხელმისაწვდომ მასალას; ახალი დიაგნოსტიკა უკვე კონკრეტულ მიზეზს ადგენს.

## დადასტურებული მიზეზი

მომხმარებლის მოწოდებული დიაგნოსტიკა გადაღებულია `2026-10-11T04:52:11.377Z`-ზე, სამუშაოსთვის `c7979442-689f-46ac-aee8-9794dd03aa53` (სკაპი, 2026-10-05 კვირა, ვერსია 1). კვირის გეგმა დასრულებულია. პოსტები შეწყდა `outline` ეტაპზე: არც დასრულებული outline და არც ტექსტი არ არსებობს.

ოთხი ცდის რვავე მოდელურ პასუხში (საწყისი პასუხი და ერთი ავტომატური შესწორება თითო ცდაზე) დარჩა `Use only channels permitted by the approved social strategy`. ორ საწყის პასუხში გამოსახულების ვიზუალური დავალების მოთხოვნაც დაირღვა; ავტომატურმა შესწორებამ ეს ნაწილი მოაგვარა. მთავარი განმეორებადი მიზეზი დაუშვებელი არხი იყო. ანგარიშში კონკრეტული აკრძალული არხი და სტრატეგიის სრული ტექსტი არ შედის; ამიტომ არ ვასახელებთ, სკაპისთვის რომელი არხია გამორთული.

კოდი დასაშვებ არხებს ადგენდა დამტკიცებული სტრატეგიისა და `channelPolicies`-ის მიხედვით, თუმცა მოდელის input-ში ეს ზუსტი სია არ შედიოდა. სქემა ყოველთვის უშვებდა Facebook-სა და Instagram-ს. ინსტრუქცია ორივე არხის არჩევას სთავაზობდა, შესწორების შეტყობინება კი დასაშვებ არხს არ ასახელებდა. შესაბამისად, განსაკუთრებით გამორთული არხის შემთხვევაში მოდელი ვერ ხედავდა იმ შეზღუდვას, რომელსაც აპლიკაცია პასუხის მიღების შემდეგ ამოწმებდა.

რვავე რეალური გამოძახება იყენებდა `gpt-5.6-terra`-ს და `medium` დონეს. ამავე სერვერზე ცალკე დიაგნოსტიკამ planner/writer/reviewer სამივეზე `gpt-6.1-sol` და დონეები `medium`/`medium`/`low` აჩვენა. ეს ადასტურებს worker-ის ბოლო რეალური გამოყენებისა და CLI-ის პარამეტრების განსხვავებას. კონკრეტულად PM2-ის ძველი გარემოა მიზეზი, ecosystem ფაილი თუ სხვა გაშვების ადგილი, ამ მასალით არ დგინდება.

## განხორციელებული ცვლილება

- planner იღებს აპლიკაციის მიერ გამოთვლილ `allowedPostChannels` სიას. სტრატეგიული რეკომენდაციები ან მომხმარებლის ტექსტი ამ სიას ვერ აფართოებს.
- გენერაციის სქემაში არხის enum და ერთ პოსტზე არხების მაქსიმალური რაოდენობა იმავე სიით იზღუდება. საცავში არსებული გეგმების საერთო სქემა უცვლელია. `enum` მხარდაჭერილია OpenAI-ის Structured Outputs-ში. [ოფიციალური აღწერა](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).
- არჩეული რაოდენობის მქონე არხზე `0` გამორიცხავს მას გენერაციის სიიდან. დაუშვებელ არხზე დადებითი რაოდენობა, ცარიელი სია ან შეუთავსებელი შენარჩუნებული პოსტები AI-ის გამოძახებამდე იბლოკება.
- აპლიკაციის არხების დამატებითი შემოწმება შენარჩუნებულია და კონკრეტულ დაუშვებელ/დასაშვებ არხებს ასახელებს. ფაქტები, მტკიცებულება, რეჟიმი, ვიზუალური ფორმატი, რაოდენობა და დამტკიცება კვლავ მოწმდება.
- გამოსახულების ინსტრუქცია ცალსახად ითხოვს ერთ graphic/photo კადრს და feed-ის პროპორციას. ეს განმარტებაა; ვიზუალური ვალიდაციის წესები არ შესუსტებულა.
- ახალი planner-ის ვერსიაა `founder-post-schedule-v8`. დამატებითი retry, სხვა მოდელზე fallback ან სტრატეგიის ავტომატური ცვლილება არ დამატებულა.

## სერვერზე გამოყენება

1. ატვირთეთ ეს ცვლილებები და ვებაპლიკაცია ჩვეულებრივი წესით განაახლეთ. ბაზის ახალი მიგრაცია საჭირო არ არის.
2. არსებული `.env.local` შეინარჩუნეთ. თუ PM2-ის ecosystem ფაილიც მოდელებს განსაზღვრავს, მისი შესაბამისი მნიშვნელობებიც იმავე პარამეტრებს უნდა ემთხვეოდეს. Node-ის `--env-file` პროცესის გარემოში უკვე არსებულ იმავე ცვლადს არ გადაფარავს. [Node-ის ოფიციალური აღწერა](https://nodejs.org/api/cli.html#--env-filefile).
3. შესაბამისი PM2 მომხმარებლით შეამოწმეთ `pm2 list` და worker-ის სახელი. მოწოდებული ლოგიდან სახელი არის `unda-worker`. განახლება შეთანხმებულ პარამეტრებს პირდაპირ გადასცემს PM2-ს:

```bash
cd /var/www/unda-app
OPENAI_POST_PLANNER_MODEL=gpt-6.1-sol \
OPENAI_POST_WRITER_MODEL=gpt-6.1-sol \
OPENAI_POST_REVIEW_MODEL=gpt-6.1-sol \
OPENAI_POST_PLANNER_REASONING_EFFORT=medium \
OPENAI_POST_WRITER_REASONING_EFFORT=medium \
OPENAI_POST_REVIEW_REASONING_EFFORT=low \
pm2 restart unda-worker --update-env
```

PM2-ის გარემოს განახლების პარამეტრი აღწერილია [ოფიციალურ ინსტრუქციაში](https://pm2.keymetrics.io/docs/usage/process-management/#updating-environment-variables-and-options). ბრძანებაში მხოლოდ მოდელების სახელები და მსჯელობის დონეებია.

4. შეამოწმეთ გადატვირთვის შემდეგ შექმნილი `Operator AI configuration` ჩანაწერი:

```bash
pm2 logs unda-worker --lines 80 --nostream
```

მოსალოდნელია outline=`gpt-6.1-sol`/`medium`, writing=`gpt-6.1-sol`/`medium`, review=`gpt-6.1-sol`/`low`. თუ ეს ჩანაწერი ვერ მოიძებნა ან მნიშვნელობები განსხვავდება, ჯერ შეამოწმეთ, რომ განახლებული worker სწორი პროექტიდან გაეშვა; პოსტების ფასიანი ცდა მანამდე არ გამეორდეს.

5. აპლიკაციაში არსებულ გეგმაზე ერთხელ დააჭირეთ პოსტების ხელახლა მომზადებას. ხელახლა ბრენდის გაცნობა და სტრატეგიის გენერაცია საჭირო არ არის.
6. მიმდინარე მცდელობის ფაქტობრივი პარამეტრები და შედეგი გადაამოწმეთ იმავე წაკითხვის დიაგნოსტიკით:

```bash
node --env-file=.env.local --import tsx scripts/weekly-posts-diagnostics.mts c7979442-689f-46ac-aee8-9794dd03aa53
```

მნიშვნელობა აქვს ახალ დროის ნიშნებს: ისტორიაში ძველი `v7`/`gpt-5.6-terra` წარუმატებელი ჩანაწერები დარჩება. ახალი `post_schedule` უნდა იყოს `v8`/`gpt-6.1-sol`/`medium`; მიღებული პასუხი აღნიშნულია `accepted`-ით. საბოლოო წარმატება არის `posts.status=ready`, `posts.step=ready` და ყველა პოსტის დასრულებული ტექსტი. დასრულებული outline მარტო საბოლოო გენერაციის წარმატებას არ ამტკიცებს.

## შემოწმების ფარგლები

ხუთი ახალი ოფლაინ ტესტი ამოწმებს მხოლოდ Facebook-ს, მხოლოდ Instagram-ს, სტრატეგიით დაშვებულ მაგრამ პოლიტიკით გამორთულ არხს, ორივე არხს, legacy გეგმას, ნულოვან cadence-ს, რეალური reasoner-ის კონტრაქტის შესწორებას, განმეორებითი დარღვევის უარყოფას და შენარჩუნებულ პოსტებზე დამატებას. გენერაციის სქემის შევიწროება არ ცვლის არსებული სქემის ობიექტს. უცნობი ფაქტი და მცდარი ვიზუალური ფორმატი კვლავ უარყოფილია.

`npm run verify` წარმატებულია: 311 domain და 234 application ტესტი — ჯამში 545 ტესტი, ნული ჩავარდნა და ნული გამოტოვება. ტიპების შემოწმება და production build წარმატებულია. კოდის სტილის შემოწმებას აქვს ექვსი არსებული გაფრთხილება და ნული შეცდომა. სრული ინტეგრაციის ნაკრები ამ ცვლილებისთვის არ გამეორებულა, რადგან შეიცვალა მხოლოდ planner-ის input, სქემა და ინსტრუქცია.

შედეგები და წყაროების ჰეშები ჩაწერილია [გადამოწმების ჩანაწერში](2026-10-11-post-channel-recovery-verification.json). ოფლაინ ტესტებში provider-ის პასუხები კონტროლდება; რეალური AI მოთხოვნა და production-ის ცვლილება არ შესრულებულა. ლაივ გენერაციის საბოლოო შედეგი ატვირთვის, worker-ის გადატვირთვისა და ერთი ცდის შემდეგ დასადასტურებელია.
