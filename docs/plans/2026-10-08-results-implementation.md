# T06 — გაზომილი შედეგების დაკავშირება კვირის დაგეგმვასთან

დასრულებულია კოდის იმპლემენტაცია, 2026-10-08. ახალი გეგმა იღებს დადასტურებული პუბლიკაციების ბოლო გაზომვებს და მომხმარებლის ცალკე აღნიშნულ ბიზნესკონტექსტს. Jev აქტიურ პროცესში არ ჩართულა.

## რა შეიცვალა

- ერთი საერთო use case ქმნის `WeekEvidence`-ს შედეგების გვერდისთვის და ახალი planning run-ისთვის. შერჩევაშია მიმდინარე და წინა სამი კვირა, თბილისის კალენდრით. პერიოდი პოსტის რეალური გამოქვეყნების დროს ეკუთვნის და არა source plan-ის თარიღს. ბოლო გაზომვა შეიძლება პუბლიკაციის კვირის შემდეგ მიღებულ რეაქციებსაც მოიცავდეს; ეს კვირის რეაქციების დელტა არ არის.
- მხოლოდ შენახული `published` შედეგი ან ვალიდური `publicationFound` reconciliation ითვლება დადასტურებულ გამოქვეყნებად. მომზადებული ტექსტი, განრიგი, გაუქმებული დაუწყებელი განრიგი, HTTP პასუხი და გაურკვეველი შედეგი თავისთავად პუბლიკაცია არ არის. გაურკვეველი მცდელობის დადასტურებულ კონკრეტულ ბმულზე ანალიტიკის მიღება მუშაობს მაშინაც, როცა პირველ journal ჩანაწერში publication reference ვერ შეინახა.
- კავშირი მოწმდება owner/workspace/brand, canonical account, channel, immutable publication input, ტექსტის ვერსია, schedule, attempt და provider binding-ის მიხედვით. Reconciliation-ს თავისი unknown result და მცდელობის ზუსტი კავშირი სჭირდება. ძველი ჩანაწერების კავშირები აგებულია კითხვისას; ეს განმეორებადი პროცესი ისტორიულ ჩანაწერებს არ გადაწერს და დაუდასტურებელ ბმულს ავტორიტეტს არ ანიჭებს.
- ერთი პოსტის snapshot-ები არ ჯამდება. არჩეულია ერთი უახლესი snapshot, რომლის წყაროს თარიღი, observation და რეალური შენახვის დრო არ აჭარბებს `asOf`-ს. ძველი snapshot-ის გამქრალი მაჩვენებელი ახალში არ გადმოდის. ნული რჩება გაზომილ ნულად; null უცნობია.
- იდენტობა ემყარება canonical account/channel/native publication reference-ს; მისი არქონისას provider-ის publication reference-ს. Binding-ის შეცვლა ისტორიას არ კარგავს. უახლეს ჩანაწერში გამოტოვებული native reference შეიძლება შენარჩუნდეს მხოლოდ წინა, ერთმნიშვნელოვანი მონაცემიდან. წინააღმდეგობრივი native reference ან ტექსტის ვერსიის კავშირი მის მაჩვენებლებს შეფასებიდან გამორიცხავს. Native identity-ის არქონისას სხვადასხვა პროვაიდერში იგივე ფიზიკური პოსტის იდენტობა დაუდგენელია და შეზღუდვა ჩანს.
- ახალი adapter ინახავს ვერსიულ field-mapping contract-ს `zernio.reported-fields.v1`. ეს არ არის engagement-ის გამყოფის, reach-ის უნიკალურობის ან სხვა provider semantics-ის დადასტურება. ძველი ან უვერსიო snapshot რჩება `legacy-unspecified`.
- ხელით დამატებული დაკვირვების provenance ყოველთვის `manual`-ია, მათ შორის მომხმარებლის მიერ `connected` ან `downstream`-ად მონიშნული ჩანაწერები. API და შენახვის use case ასეთ მონაცემს ავტომატურ results authority-ს არ აძლევს. მისი შესრულების აღწერა და შეზღუდვები ცალკე რჩება. ძველი payload-ის `available` სტატუსიც ავტომატურ გაზომვად არ განიმარტება.
- ავტომატური გაზომვების მდგომარეობაა `unavailable`, `partial` ან `available`. სრული მდგომარეობა ნიშნავს დასრულებულ, შეუზღუდავ პერიოდს, ცნობილ native identity-ს და ყველა ნაჩვენები პოსტის ყველა ათი ველის გაზომვას. ეს ბიზნესმიზნის მიღწევის ან მიზეზობრივი ეფექტის შეფასება არ არის.
- ახალი run ინახავს შერჩევის სრულ snapshot-ს. ახალი გაზომვა და ბიზნესკონტექსტის რედაქტირება არსებულ გეგმას არ ცვლის; იდემპოტენტური `begin` ხელახლა არ აგროვებს შედეგებს. ახალი ვერსიის შექმნა ახალ snapshot-ს აიღებს. მიმდინარე results გვერდს შეუძლია უფრო ახალი მონაცემი აჩვენოს.

## დროისა და მოცულობის კონტროლი

დამატებითი მოდელის გამოძახება არ ხდება. თითოეული კვირის snapshot ინახავს მაქსიმუმ 12 პოსტს, უახლესი გამოქვეყნების მიხედვით; კითხვის საერთო ზღვარია 400 დადასტურებული delivery ჩანაწერი, დამატებით ერთი ჩანაწერი შეზღუდვის გამოსავლენად. შეზღუდული შერჩევა მონიშნულია და სრულ პერიოდად არ განიმარტება. პოსტებსა და snapshot-ებზე reach/engagement არ ჯამდება და არ იქმნება ავტომატური გამარჯვებულების რეიტინგი.

მოდელს გადაეცემა მხოლოდ გადაწყვეტილებისთვის საჭირო გაზომვები, ასაკი, წყარო, contract, ვერსია და შეზღუდვები. სრული lineage და ტექნიკური ID-ები რჩება შენახულ snapshot-ში. ცარიელი კვირების ერთნაირი აღწერები და გაზომვების დიდი დუბლირებული ასლები მოდელის კონტექსტში არ იგზავნება.

ეს ამცირებს ზედმეტ კონტექსტს და გამორიცხავს ახალ მოდელურ ნაბიჯს. წარმოებაში რეალური latency-ის, ღირებულების ან კონტენტის ხარისხის გაუმჯობესება ამ სამუშაოში არ გაზომილა.

## მომხმარებლის გამოცდილება

შედეგების გვერდზე კვირის არჩევა, დადასტურებული პუბლიკაციების რაოდენობა, გაზომვების მდგომარეობა და მონაცემების აღების დრო ჩანს. პოსტთან ნაჩვენებია გამოქვეყნების/გაზომვის დრო, გაზომვისას პოსტის ასაკი, ტექსტის ვერსია და წყარო. ბიზნესკონტექსტი ცალკე ბლოკშია. ზუსტი განმარტებები გასაშლელ ბლოკში რჩება, ხოლო მიზანი და შემდეგი მოქმედება მთავარ ხედში ჩანს.

სტატიკური UI ნიმუში გამოგონილი მონაცემებით ვიზუალურად შემოწმებულია Chrome-ში კომპიუტერისა და მობილურის ზომებზე. მობილურ ხედში ჰორიზონტალური გადაცდენა არ დაფიქსირდა. ეს არ არის ავტორიზებული production გვერდის ან hydration/კვირის გადართვის end-to-end შემოწმება.

## განთავსება და დარჩენილი საზღვრები

ახალი მიგრაციაა `0022_result_evidence.sql`: metric contract, შედეგის რეალური ჩაწერის დრო და გამოქვეყნების ინდექსები. არსებული მონაცემებისთვის ეს ახალი ჩაწერის დრო migration-ის დროს ივსება; მის წინა ისტორიულ capture დროს არ ვიგონებთ. Docker-ის საერთო ლოკალურ ბაზაში read-only შემოწმებამ გამოავლინა, რომ 0020, 0021 და 0022 ჯერ გასაშვებია. ისინი მხოლოდ იზოლირებულ ტესტებში შესრულდა; საერთო მონაცემები არ შეცვლილა.

განთავსებისას საჭიროა წინა T04/T05 rollout წესის დაცვა: scheduling ჩაწერებისა და delivery workers-ის დროებით შეჩერება, მიგრაციები და API/worker ვერსიების შეთანხმებული განახლება, smoke შემოწმება და შემდეგ რიგების ჩართვა. Production არ განთავსებულა და რეალური სოციალური გამოქვეყნება არ შესრულებულა.

ეს ეტაპი ავტომატურად არ ცვლის სტრატეგიულ მიზანს და არ ქმნის გაყიდვების attribution-ს. ხელით შენახულ შეფასებას საკუთარი ისტორიული ვერსიების ცხრილი ჯერ არ აქვს; კონკრეტულ გეგმაში გამოყენებული ვარიანტი ინახება მის frozen snapshot-ში. ოთხ კვირაზე ძველი შენიშვნა ამ bounded planning input-ში არ შედის. სხვადასხვა პროვაიდერში native identity-ის გარეშე ფიზიკური პოსტის გაერთიანებას არ ვვარაუდობთ.

შემდეგი ეტაპია T08 — საერთო კვირის განრიგი, ატომური შენახვა, დროის სარტყელი და უსაფრთხო reschedule/cancel.
