# კვირის გეგმა და პოსტები

ფაუნდერი კვირის ეკრანზე ხედავს სტრატეგიას და Facebook/Instagram-ის პოსტების რედაქტირებად რაოდენობას. ცალკე კონტენტის ტაბში ჩანს პოსტების შეთავაზებული დღეები, არხები, ფორმატები, სრული ტექსტები და რეკომენდებული ვიზუალები. ერთ პოსტს შეიძლება ორი არხის ვერსია ჰქონდეს; პოსტებისა და განთავსებების რაოდენობა ცალ-ცალკე ჩანს.

სტრატეგია, აუდიტორიები, არჩეული მიზნები, communication envelope და დასაბუთება შენარჩუნებულია კვირის ტაბში; დამატებითი დეტალები ჩამოსაშლელ ნაწილებშია. პოსტები არ გამოქვეყნდება ავტომატურად: დღეები და არხები ამ ეტაპზე რეკომენდაციებია.

## პროცესი

1. დადასტურებული ბრენდის ცოდნა და ფაუნდერის კვირის პრიორიტეტი → ერთი სტრუქტურირებული სტრატეგიული გადაწყვეტილება → დამოუკიდებელი შემოწმება.
2. სტრატეგია → 2–5 კონკრეტული პოსტის შეთავაზება, თითოეულის brief, არხი, ფორმატი და ვიზუალური დავალება.
3. მაქსიმუმ სამი პოსტის ტექსტი მზადდება პარალელურად. თითოეული დასრულებული ტექსტი ცალკე ინახება და ეკრანზე ჩნდება.
4. სრული ტექსტები მოწმდება ფაქტებთან, ბრენდის ხმასთან და დავალებასთან. პრობლემურ ტექსტებზე ავტომატურად კეთდება ერთი გასწორება. დარჩენილი პრობლემების შემთხვევაში ფაუნდერს შეუძლია მხოლოდ ამ პოსტების ხელახლა გასწორება; სწორი ტექსტები და გეგმა შენარჩუნებულია.
5. ფაუნდერი ადასტურებს გეგმასა და ტექსტებს. ძველი სტრატეგიის დადასტურება ახალ ტექსტებს ავტომატურად არ ადასტურებს. ახალი ვერსიის მზადებისას წინა დამტკიცებული გეგმა, ტექსტები და გამოსახულებები ხელმისაწვდომია.

ჩვეულებრივი პოსტისთვის მზადდება სრული caption, კარუსელისთვის — caption და ყველა სლაიდის ტექსტი, სთორისთვის — კადრების ტექსტები, რილისთვის — სცენარი და ეკრანის ტექსტები. ტექსტური პოსტი Instagram-ზე არ იგეგმება. რილი მოითხოვს ვიდეოს გადაღებას; ვიდეოს გენერაცია/ატვირთვა ამ ვერსიაში არ არის დამატებული.

## გამოსახულებები

საკუთარი JPG, PNG ან WebP ფაილის ატვირთვა, ნახვა, ჩანაცვლება და წაშლა შესაძლებელია პოსტზე ან კონკრეტულ სლაიდზე. ლიმიტი: 8 MB ფაილზე, 20 მილიონი პიქსელი დეკოდირებისას და 100 MB ანგარიშზე. ფაილი მოწმდება რეალური შინაარსით, იშლება მეტამონაცემები და ინახება WebP ფორმატში, მაქსიმუმ 2400 პიქსელამდე. ფაილები PostgreSQL-ში ინახება და ხელმისაწვდომია მხოლოდ მფლობელისთვის.

გამოსახულების გენერაცია ხელმისაწვდომია პოსტის ვიზუალის პანელში. development/demo/test რეჟიმში სამუშაო სივრცე ერთხელ იღებს 20 კრედიტს; production-ში ავტომატური შევსება არ ხდება. თითოეული წარმატებული სურათი ღირს 1 კრედიტი, წარუმატებელი — 0. შედეგი ინახება ისტორიაში და პოსტზე მიმაგრება ცალკე მოქმედებაა. კონფიგურაცია და შემოწმება აღწერილია [ვიზუალების გენერაციის დოკუმენტაციაში](visual-generation.md).

## მოდელები და სიჩქარე

ნაგულისხმევია GPT-5.6 Terra სტრატეგიისთვის, პოსტების ჩამონათვალისა და შემოწმებისთვის; GPT-5.6 Sol — პოსტების ტექსტებისთვის. პოსტების სამივე ეტაპი იყენებს `reasoning.effort=low`-ს. ხარისხი ინარჩუნებს პრიორიტეტს. ძველი ხუთი თანმიმდევრული სტრატეგიული გამოძახება ერთში გაერთიანდა, შემოწმება დამოუკიდებლად დარჩა; პოსტები მაქსიმუმ სამ-სამად მზადდება. ყველა ეტაპი შენახულია და წარუმატებელი ტექსტის გამო დასრულებული ტექსტები თავიდან არ იწერება.

წინა, ყველა ეტაპზე Sol-ის გამოყენებით ჩატარებულ საჯარო Asylum-ის საცდელ გაშვებაში სამივე პოსტის წერა პარალელურად დაახლოებით 31 წამში დასრულდა; ცალ-ცალკე დროები იყო 11, 17 და 31 წამი. პოსტების ჩამონათვალმა 65 წამი, შემოწმებამ 13 წამი წაიღო. ეს ერთი გაშვების გაზომვებია და არა დაპირებული დრო მთელი პროცესისთვის. სხვა გაშვებასა და გასწორებას შეიძლება მეტი დრო დასჭირდეს.

Terra-ს იმავე საჯარო ბრენდის საცდელმა გეგმამ 52 წამი წაიღო, თუმცა ვიზუალური დატვირთვა და მიმართულებების გამეორება ნაკლებად სასურველი აღმოჩნდა; იმ ვერსიაში ნაგულისხმევი მოდელი Sol დარჩა. ახალი reliability-ბრიფის მიხედვით ჩამონათვალი და შემოწმება Terra-ზე გადადის; წერა Sol-ზე რჩება. ახალი განაწილების სიჩქარე რეალურ გენერაციაზე ამ ცვლილების ფარგლებში ხელახლა არ გაზომილა. დამატებითი `none` რეჟიმის შედარება არ დასრულებულა და წარმოებისთვის არ არჩეულა.

წყაროები: [Sol-ის შესაძლებლობები](https://developers.openai.com/api/docs/models/gpt-5.6-sol), [Terra-ის შესაძლებლობები](https://developers.openai.com/api/docs/models/gpt-5.6-terra), [OpenAI-ის სიჩქარის მითითებები](https://developers.openai.com/api/docs/guides/latency-optimization).

## სერვერზე განახლება

1. ჩვეულებრივი წესით განაახლეთ პროექტი და დააყენეთ lockfile-ის დამოკიდებულებები: `npm ci`.
2. აპლიკაციის ახალი ვერსიის გაშვებამდე გაუშვით `npm run db:migrate`. საჭიროა `0008_weekly_planning.sql`, `0009_weekly_posts.sql` და `0010_weekly_post_capacity.sql`; უკვე შესრულებულ მიგრაციებს სკრიპტი გამოტოვებს.
3. მოამზადეთ `npm run build` და გადატვირთეთ ვებპროცესი.
4. გადატვირთეთ მუდმივი worker: `npm run worker:operator`. არსებული `worker:discovery` იგივე პროცესს უშვებს და ბრენდის გაცნობასთან ერთად კვირის გეგმასა და პოსტებსაც ემსახურება. ჰოსტის process manager-მა worker მუდმივად უნდა ამუშაოს, რათა ბრაუზერის დახურვის შემდეგაც გაგრძელდეს მუშაობა.
5. `OPENAI_API_KEY` საჭიროა. მოდელების სრული განაწილება და სერვერზე დასაყენებელი ცვლადები აღწერილია [reliability-ის ცვლილებაში](ai/Post%20Generation%20Reliability%20—%20Implementation.md). არსებული `.env.local` ავტომატურად არ იცვლება.

გამოსახულებების ცალკე საცავისა და გენერაციის გასაღების გამართვა ამ ეტაპზე საჭირო არ არის. ატვირთული ფაილები მონაცემთა ბაზის სარეზერვო ასლშიც ხვდება.

## შემოწმება

`npm run test:planning` ამოწმებს კონტრაქტებს, უცნობ/დუბლირებულ მითითებებს, ფორმატებს, არხებს, ტექსტების ნაწილობრივ შენახვას, მფლობელის წვდომას, ატვირთვებს, დადასტურებას, კონკრეტული პოსტების გასწორებას, ძველი ვერსიის შენარჩუნებას და განახლებულ ბრენდის ცოდნასთან კონფლიქტს. რეალური ბაზის ტესტი მუშაობს იზოლირებულ დროებით სქემაში და მოდელის პასუხებისთვის იყენებს სატესტო მონაცემებს.

საერთო შემოწმება: `npm test`, `npm run lint`, `npm run build`. მიმდინარე ცვლილებებში სოციალური ანგარიშების დაკავშირება, რეალური გამოქვეყნება, ანალიტიკა და ფასიანი გამოწერის გააქტიურება არ შედის.


## კვირისა და კონტენტის განაწილება — 7 სექტემბრის განახლება

კვირის ტაბში ჩანს ბიზნესზე მორგებული სტრატეგია და Facebook/Instagram-ის რაოდენობის ცალკე არჩევანი. კონტენტის ტაბი დაკავშირებულია იმავე ბრენდსა და კვირასთან: მასში ჩანს რეალური ტექსტები, ვიზუალური დავალებები, ატვირთვები, არხების ფილტრი და შეთავაზებული დღეების განრიგი. ნავიგაცია ინარჩუნებს არჩეულ კვირას. სერვერზე შენახული მდგომარეობა მოწმდება პერიოდულად ორივე ტაბში, მაშინაც, როცა სხვა ჩანართში შეიცვალა ვერსია.

სტრატეგიის შემოწმების დასრულებისას პოსტების მომზადება ავტომატურად იწყება. რაოდენობა გამოჩნდება ჩამონათვალის მომზადებისთანავე, ტექსტების დასრულებამდე. ძველი გეგმისთვის, რომელსაც პოსტების პროცესი საერთოდ არ აქვს, რჩება აშკარა ღილაკი „პოსტების მომზადება“. ახალი ბრენდისთვის კვირის გეგმაც ცალკე უნდა მოითხოვოთ; ბრენდის შექმნა ყველა კვირას ავტომატურად არ ქმნის.

ფაუნდერი ირჩევს 0–5 პოსტს თითო არხზე. 0 აჩერებს არხს ამ კვირისთვის; ორივეგან 0 აჩერებს მთელი კვირის პოსტების მომზადებას. ერთი პოსტი შეიძლება ორივე არხზე იყოს; მათი ჯამი განთავსებების რაოდენობაა და არა უნიკალური პოსტების რაოდენობა.

ცვლილება იგზავნება მხოლოდ „რაოდენობის შენახვა და განრიგის განახლება“ ღილაკით. უცვლელი რაოდენობის გაგზავნა ახალ ვერსიას ან ხარჯს არ ქმნის. შენახვა ქმნის ახალ ვერსიას, არსებული სტრატეგიისა და ბრენდის საფუძვლის გამოყენებით. შემცირებისას რჩება არსებული პოსტების რიგით პირველი საჭირო პოსტები შესაბამისი არხების ტექსტებითა და ატვირთვებით; გაზრდისას დამგეგმავი ქმნის მხოლოდ დანაკლისს. დღეები თავიდან ნაწილდება დარჩენილ კვირაზე, შემდეგ მოწმდება მთელი ტექსტური თანმიმდევრობა. თუ შემცირების შედეგად აუცილებელი შინაარსი დაიკარგა, შემოწმებამ შეიძლება მოითხოვოს დარჩენილი ტექსტის დაზუსტება.

წინა დადასტურებული გეგმა და კონტენტი შენარჩუნებულია ახალის დადასტურებამდე. ატვირთვები, რომლებიც დარჩენილ პოსტებს ეკუთვნის, გადადის ახალ ვერსიაში და მათი წინა ასლი ისტორიაში რჩება; ორივე ასლი ანგარიშის 100 MB კვოტაში ითვლება. მოძველებული ფონური პროცესის შენახვის უფლება უქმდება; უკვე გაგზავნილი მოდელის მოთხოვნა შეიძლება მაინც დაიხარჯოს, მაგრამ მისი პასუხი ახალ ვერსიას ვერ გადაწერს. ჩვეულებრივი სტრატეგიის დაზუსტება ხელახლა ამზადებს პოსტებს, რადგან მათი საფუძველიც იცვლება.

## თუ განახლების შემდეგ ძველი ეკრანი ჩანს

`db:migrate`-ის წინა ვერსია არაფერს ბეჭდავდა, როცა ყველა ადგილობრივი მიგრაცია უკვე შესრულებული იყო. ამიტომ ჩუმად დასრულება თავისთავად შეცდომა არ არის. ამავე დროს, ეს არ ამტკიცებს, რომ სერვერზე ახალი კოდი ან worker მუშაობს.

ამ განახლების ატვირთვის შემდეგ გაუშვით:

```bash
npm ci
npm run db:migrate
npm run build
npm run db:status
```

შემდეგ არსებული process manager-ით გადატვირთეთ როგორც ვებაპლიკაცია, ისე `worker:operator` (ან ძველი `worker:discovery`). ახალი worker-ის მხოლოდ SSH სესიაში დროებით გაშვება მუდმივ ფონურ მუშაობას ვერ უზრუნველყოფს.

მიგრაცია ახლა ბეჭდავს მოძებნილი ფაილების, შესრულებული და უკვე შესრულებული მიგრაციების რაოდენობას. `db:status` მხოლოდ კითხულობს მდგომარეობას: აჩვენებს checkout-ის ვერსიას, დისკზე წარმოების build-ის დროს, მიგრაციების დანაკლისს და პოსტების პროცესების საერთო რაოდენობას/ეტაპებს. არ ბეჭდავს პაროლებს, API გასაღებებს, ბრენდებს ან პოსტების ტექსტებს და არ იძახებს მოდელს. ამ განახლების ბოლო მიგრაციის სახელია `0010_weekly_post_capacity.sql`; მოსალოდნელია `Pending migrations: none`. ეს სკრიპტი ვერ ამტკიცებს, რომ უკვე გაშვებული ვებპროცესი ან worker გადატვირთულია — მათი სტატუსი ჰოსტის process manager-ში გადაამოწმეთ.

ფაუნდერის მოკლე შემოწმება: არსებული გეგმის კვირაში ნახეთ Facebook/Instagram-ის რაოდენობები; გადადით კონტენტში და ნახეთ ტექსტები; შეამცირეთ ერთი არხის რაოდენობა, შეინახეთ და გადაამოწმეთ განრიგი. ბრენდის თავიდან გაცნობა ამისთვის საჭირო არ არის.


## შესრულების მფლობელი და გრძელვადიანი მოთხოვნები

კვირისა და ბრენდის API მხოლოდ ამოწმებს და ინახავს მოთხოვნას; მძიმე სამუშაოს ასრულებს მუდმივი `worker:operator`. ბრაუზერის გახსნა, განახლება ან `resume` მოთხოვნა მოდელის შესრულებას აღარ უშვებს. Worker საჭიროა ლოკალური განვითარების დროსაც.

მოდელის თითო მოთხოვნის timeout არის 150 წამი. მხოლოდ დროებითი შეცდომა მეორდება ერთხელ, 1-წამიანი პაუზით. კონტრაქტის არსებული ერთი გასწორება დამოუკიდებლად რჩება, მაგრამ დროებითი შეცდომის retry მთელი ლოგიკური გამოძახებისთვის საერთოა: მაქსიმუმ 3 მოთხოვნა, 451 წამი. ეტაპის დასაწყებად worker იტოვებს 480 წამს; მისი გაშვების ბიუჯეტია 540 წამი, claim-ის დაცვა — 600 წამი. ბაზის ახალი მიგრაცია ამ ცვლილებას არ სჭირდება.
